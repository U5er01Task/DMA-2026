## 1. Экосистема пакетов Dart: архитектура пакетного менеджера Pub

Все внешние библиотеки во Flutter делятся на две принципиально разные категории:

- **Pure Dart Packages (Чистые Dart-пакеты):** Содержат только код на языке Dart (например, `intl`, `dio`, `bloc`). Работают на всех поддерживаемых платформах без ограничений.
- **Flutter Plugins (Плагины):** Пакеты, объединяющие Dart API и нативный код под конкретные платформы: Kotlin/Java для Android, Swift/Objective-C для iOS/macOS, C++ для Windows/Linux, JavaScript/Wasm для Web (например, `camera`, `geolocator`, `shared_preferences`).

```
                    ┌───────────────────────────────────┐
                    │      Клиентский код (Flutter)     │
                    └─────────────────┬─────────────────┘
                                      │
         ┌────────────────────────────┴────────────────────────────┐
         ▼                                                         ▼
┌──────────────────┐                                     ┌──────────────────┐
│  Pure Dart Lib   │                                     │  Flutter Plugin  │
│  (dio, bloc)     │                                     │  (geolocator)    │
└──────────────────┘                                     └────────┬─────────┘
                                                                  │ MethodChannel / FFI
                                                         ┌────────┴────────┐
                                                         ▼                 ▼
                                                   Android (Java)    iOS (Swift)
```

## Тема 1. Категории зависимостей и семантическое версионирование (SemVer)

В конфигурационном файле `pubspec.yaml` зависимости разделены на три изолированные секции:

1. `dependencies:` Библиотеки, необходимые для работы приложения в релизной сборке (рантайм).
2. `dev_dependencies:` Инструменты, нужные только разработчику во время сборки и тестирования (линтеры, раннеры тестов, кодогенераторы). В релизный APK/IPA не попадают.
3. `dependency_overrides:` Принудительное переопределение версий транзитивных зависимостей для экстренного устранения конфликтов.

### Принцип семантического версионирования (SemVer: MAJOR.MINOR.PATCH)

Формат номера версии: `2.4.1`

- **MAJOR (2):** Ломающие изменения (Breaking changes). Обратная совместимость нарушена.
- **MINOR (4):** Новый функционал с сохранением обратной совместимости.
- **PATCH (1):** Исправление ошибок без добавления новых методов.

### Синтаксис каретки (`^` Caret Syntax)

- `^1.2.3` эквивалентно диапазону `>=1.2.3 <2.0.0` (разрешены любые обновления, не ломающие API).
- Для версий до 1.0.0 правило меняется: `^0.2.3` эквивалентно `>=0.2.3 <0.3.0` (так как в ранних версиях любое изменение MINOR считается ломающим).

### Пример манифеста pubspec.yaml

```yaml
name: dependency_demo_app
description: "Пример настройки зависимостей"
version: 1.0.0+1

environment:
  sdk: ">=3.3.0 <4.0.0"

dependencies:
  flutter:
    sdk: flutter

  # Рантайм-зависимости (SemVer)
  dio: ^5.4.1 # Разрешено обновление до 5.9.9, но не 6.0.0
  flutter_bloc: 8.1.3 # Строгая фиксация конкретной версии (без каретки)
  uuid: ">=4.0.0 <4.3.0" # Явный интервал версий

dev_dependencies:
  flutter_test:
    sdk: flutter
  flutter_lints: ^3.0.0
  build_runner: ^2.4.8 # Движок кодогенерации (только для dev)

# Экстренное исправление конфликтов транзитивных библиотек
dependency_overrides:
  meta: 1.12.0
```

### Задания для закрепления

1. **Расшифровка диапазонов версий:** Запишите, какие конкретные версии допустимы для записей: `^2.1.0`, `^0.4.5`, `>=1.0.0 <=1.5.0`.
2. **Перенос генераторов:** Объясните письменно, почему пакет `build_runner` должен находиться строго в `dev_dependencies`, а не в `dependencies`.
3. **Фиксация точной версии:** Перепишите зависимость `path_provider` так, чтобы пакетный менеджер никогда не обновлял её автоматически без явного указания разработчика.
4. **Конфликт транзитивных библиотек:** Смоделируйте ситуацию, когда библиотека `A` требует `crypto: ^3.0.0`, а библиотека `B` требует `crypto: ^2.1.0`. Напишите блок `dependency_overrides` для принудительного выбора версии 3.0.0.
5. **Антипаттерн версии any:** Объясните, какие критические риски для стабильности промышленного проекта несет указание версии `package_name: any`.

## Тема 2. Источники пакетов: pub.dev, Git, локальные пути и приватные реестры

Dart позволяет подключать код не только из центрального репозитория `pub.dev`, но и из закрытых корпоративных серверов, репозиториев GitHub/GitLab и локальной файловой системы.

### Примеры декларации различных источников

```yaml
dependencies:
  # 1. Центральный публичный репозиторий pub.dev
  intl: ^0.19.0

  # 2. Прямая ссылка на Git-репозиторий
  custom_ui_kit:
    git:
      url: https://github.com/company/custom_ui_kit.git
      ref: v1.4.0 # Тег, имя ветки или конкретный SHA-коммит

  # 3. Git-репозиторий с вложенным пакетом (монорепозиторий)
  shared_models:
    git:
      url: git@gitlab.com:enterprise/mobile-monorepo.git
      path: packages/shared_models # Относительный путь внутри репозитория

  # 4. Локальный пакет на жестком диске разработчика
  core_network:
    path: ../packages/core_network

  # 5. Приватный защищенный корпоративный реестр (Self-hosted Pub)
  internal_auth:
    hosted:
      name: internal_auth
      url: https://pub.internal-company.ru
    version: ^2.0.0
```

> [!TIP]
> Для аутентификации в корпоративном реестре пакетов используется консольная утилита:
> `dart pub token add https://pub.internal-company.ru`

### Задания для закрепления

1. **Подключение ветки feature из Git:** Напишите блок подключения пакета из репозитория GitHub по ветке `feature/dark-theme`.
2. **Фиксация по хэшу коммита:** Сконфигурируйте подключение Git-пакета с фиксацией по полному 40-значному SHA-хэшу коммита для защиты от изменений в ветке.
3. **Локальный модуль-пакет:** Создайте рядом с проектом папку `packages/my_math`, инициализируйте там чистый Dart-пакет и подключите его в основное приложение через `path`.
4. **Переопределение публичного пакета на локальный форк:** Используя `dependency_overrides`, замените публичную библиотеку `http` на её локально скачанную копию с вашими правками.
5. **Разбор структуры hosted:** Напишите структуру декларации пакета, загружаемого со стороннего защищенного хостинга JFrog Artifactory.

## Тема 3. Алгоритм разрешения конфликтов и роль pubspec.lock

Поиск совместимых версий пакетов выполняет математический алгоритм **PubGrub** (вариант решения задачи выполнимости булевых формул SAT-solver).

```
          pubspec.yaml (Пожелания разработчика: ^1.0.0, ^2.1.0)
                                 │
                                 ▼
                     [ Алгоритм PubGrub ] ◄── Каталог pub.dev
                                 │
             ┌───────────────────┴───────────────────┐
             ▼ Успех                                 ▼ Конфликт
      pubspec.lock                            Ошибка: Version Solving Failed!
 (Зафиксирован полный граф)             (Показаны несовместимые требования)
```

### Назначение файла pubspec.lock

Файл `pubspec.lock` фиксирует:

- Точный номер версии каждой прямой и транзитивной зависимости.
- Контрольную сумму архива (Content Hash) для защиты от подмены кода на сервере.
- Источник загрузки пакета.

### Ключевые консольные команды пакетного менеджера

| Команда                                | Действие                                                                                  |
| :------------------------------------- | :---------------------------------------------------------------------------------------- |
| `flutter pub get`                      | Скачивает зависимости строго по `pubspec.lock` (не меняет зафиксированные версии)         |
| `flutter pub upgrade`                  | Обновляет зависимости до максимально возможных версий в рамках ограничений `pubspec.yaml` |
| `flutter pub outdated`                 | Анализирует и выводит таблицу устаревших пакетов с рекомендациями                         |
| `flutter pub upgrade --major-versions` | Автоматически повышает мажорные версии прямо в файле `pubspec.yaml`                       |
| `flutter pub deps`                     | Выводит полное дерево прямых и транзитивных зависимостей проекта                          |

### Задания для закрепления

1. **Анализ дерева через pub deps:** Запустите команду `flutter pub deps --style=compact` и определите глубину самого длинного пути транзитивных библиотек.
2. **Эксперимент с обновлением:** Зафиксируйте в `pubspec.yaml` версию `shared_preferences: ^2.0.0`, выполните `flutter pub get`, проверьте версию в `pubspec.lock`, а затем выполните `flutter pub upgrade`.
3. **Аудит устаревших пакетов:** Запустите `flutter pub outdated` и расшифруйте значения столбцов: `Current`, `Upgradable`, `Resolvable`, `Latest`.
4. **Удаление кэша зависимостей:** Очистите глобальный системный кэш пакетов с помощью команды `dart pub cache clean` и заново восстановите проект.
5. **Проверка целостности хэша:** Найдите в файле `pubspec.lock` поле `integrity` у пакета `flutter_lints` и объясните его роль в предотвращении атак на цепочку поставок (Supply Chain Attacks).

## Тема 4. Кодогенерация и dev-инструментарий: связка build_runner

В Flutter для генерации шаблонного кода (сериализация JSON, неизменяемые модели Freezed, внедрение зависимостей, роутинг) используется пакет `build_runner`.

### Архитектурное разделение: Аннотации против Генераторов

- В `dependencies` добавляются легковесные пакеты, содержащие только аннотации (`json_annotation`, `freezed_annotation`).
- В `dev_dependencies` добавляются тяжелые генераторы кода и сам раннер (`build_runner`, `json_serializable`, `freezed`).

```yaml
dependencies:
  flutter:
    sdk: flutter
  json_annotation: ^4.8.1 # Только маркеры @JsonSerializable()

dev_dependencies:
  build_runner: ^2.4.8 # Исполнитель кодогенерации
  json_serializable: ^6.7.1 # Модуль, генерирующий *.g.dart файлы
```

### Пример генерации модели данных

```dart
// Файл: lib/models/product.dart
import 'package:json_annotation/json_annotation.dart';

// Связь с будущим сгенерированным файлом
part 'product.g.dart';

@JsonSerializable()
class Product {
  final int id;
  final String title;
  final double price;

  const Product({required this.id, required this.title, required this.price});

  // Фабрика делегирует парсинг сгенерированной функции
  factory Product.fromJson(Map<String, dynamic> json) => _$ProductFromJson(json);

  Map<String, dynamic> toJson() => _$ProductToJson(this);
}
```

Запуск генерации из терминала:

```bash
# Однократная генерация с перезаписью конфликтов:
dart run build_runner build --delete-conflicting-outputs

# Непрерывный режим отслеживания изменений (Watch mode):
dart run build_runner watch --delete-conflicting-outputs
```

### Задания для закрепления

1. **Настройка связки json_serializable:** Подключите в проект `json_annotation` и `json_serializable` и сгенерируйте файл `user.g.dart` для класса `User`.
2. **Конфигурация build.yaml:** Создайте в корне проекта файл `build.yaml` и настройте генерацию JSON так, чтобы все поля по умолчанию переводились в `snake_case`.
3. **Очистка сгенерированного кода:** Используя команду `dart run build_runner clean`, очистите временные кэши сборщика генераторов.
4. **Исключение из Git:** Добавьте в файл `.gitignore` правило исключения служебных кэшей сборщика `.dart_tool/build/`.
5. **Параллельная генерация:** Запустите генерацию с флагом замера времени выполнения и объясните влияние директивы `part / part of` на скорость работы инкрементального анализатора.

## Тема 5. Нативные плагины и связка с платформами (Gradle / CocoaPods)

Когда в проект подключается плагин с нативным кодом, в процесс сборки автоматически включаются платформенные сборочные системы.

### Связка с Android (Gradle)

Плагин внедряется как дочерний Gradle-субпроект. Частые причины ошибок при подключении плагинов:

- **Несоответствие `minSdkVersion`:** Плагин требует API 24 (Android 7.0), а в приложении выставлен API 21 (Android 5.0).
- **Конфликт дублирующихся классов:** Несовместимость библиотек поддержки Android Support и современной библиотеки AndroidX.
- **Отсутствие плагина Kotlin:** Плагин написан на Kotlin, а проект не имеет настроенного плагина `org.jetbrains.kotlin.android`.

### Связка с iOS / macOS (CocoaPods)

Пакетный менеджер CocoaPods считывает зависимости из `ios/Podfile`:

- Файл `Podfile.lock` фиксирует нативные iOS-библиотеки (Pods / Frameworks).
- Минимальная версия системы: директива `platform :ios, '13.0'` в начале файла `Podfile`.

```bash
# Типовой протокол очистки и восстановления нативных зависимостей iOS:
cd ios
rm -rf Pods Podfile.lock .symlinks
pod cache clean --all
pod repo update
pod install
cd ..
flutter run
```

### Задания для закрепления

1. **Подключение плагина геолокации:** Добавьте в проект плагин `geolocator` и проанализируйте, какие изменения появились в файле `android/app/build.gradle` после `flutter pub get`.
2. **Подъем minSdkVersion:** Исправьте ошибку сборки плагина биометрии `local_auth`, подняв версию `minSdkVersion = 23` в скрипте Gradle.
3. **Диагностика CocoaPods:** Выполните в терминале команду `pod outdated` внутри папки `ios/` и определите нативные зависимости фреймворка Flutter.
4. **Проверка разрешений плагина:** Добавьте плагин камеры `camera` и внесите обязательные строковые ключи описания разрешений в манифест Android и файл `Info.plist` iOS.
5. **Сборка без нативных плагинов:** Проверьте возможность компиляции приложения в Web-версию (`flutter build web`) при наличии плагина, не поддерживающего Web-платформу.

## 50 Смешанных заданий по управлению зависимостями

1. **Разрешение тупика зависимостей (Version Incompatibility):** Пакет `A` требует `intl: ^0.18.0`, а пакет `B` требует `intl: ^0.19.0`. Решите проблему через `dependency_overrides` и оцените риски рантайм-крашей.
2. **Снятие ограничения каретки для пре-релиза:** Подключите альфа-версию библиотеки `flutter_bloc: 9.0.0-alpha.1` с правильной фиксацией пре-релизного тега.
3. **Аудит безопасности зависимостей:** Проверьте зависимости проекта на наличие известных уязвимостей с помощью сторонних сканеров или встроенного `dart pub audit`.
4. **Откат версии пакета:** Понизьте версию сетевого клиента `dio` на один минорный релиз назад через файл манифеста и команду `flutter pub downgrade`.
5. **Блокировка мажорных обновлений в CI:** Настройте команду запуска `flutter pub get --enforce-lockfile` в пайплайне сборщика для запрета неконтролируемого изменения `pubspec.lock`.
6. **Выявление дублирующихся библиотек:** Найдите с помощью `flutter pub deps` пакеты, реализующие схожий функционал (например, одновременное подключение `http` и `dio`).
7. **Поиск устаревших не-Null-Safe библиотек:** Проверьте зависимости на совместимость с современными стандартами Sound Null Safety.
8. **Ограничение платформенной совместимости:** Объявите в манифесте секцию `platforms:` с указанием поддержки только `android` и `ios`.
9. **Контроль размера бандла (App Size Analysis):** Соберите приложение с флагом `--analyze-size` и определите, какая библиотека занимает наибольший объем в мегабайтах.
10. **Миграция с устаревшего пакета:** Замените заброшенный пакет сохранения настроек на актуальный `shared_preferences`, написав адаптер совместимости интерфейсов.

### Блок 2: Мультимодульные монорепозитории и Git-пакеты (11–20)

11. **Проектирование монорепозитория:** Создайте проект с корневым приложением `app/` и тремя локальными пакетами в папке `packages/`: `api_client`, `ui_kit`, `core_utils`.
